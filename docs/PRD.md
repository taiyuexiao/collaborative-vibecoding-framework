| 版本 | 日期 | 作者 | 状态 |
|---|---|---|---|
| v0.1 | 2026-09-06 | spl × ZCode | 初稿（MVP 范围） |

## 1. 产品定位

共工是一个给「人 + 各自带 agent 团队的成员」使用的**团队协作操作系统**：

> 让人管理工作（work），让 agent 消化协作的开销（coordination overhead）。

它不替代任何 coding agent（Claude Code / zcode / Codex CLI…），也不替代 IM（飞书/微信）与代码托管（Gitee/GitHub），而是充当三者之上的**组织协议层**：

- **任务总线**：所有跨人协作请求以结构化任务流转，替代群里口头发散的指令
- **会话桥**：每个成员本地的 agent 会话接入同一工作面，状态可感知、任务可派发
- **冲突雷达**：在途任务的文件/契约冲突提前预警，替代"合并时才发现"
- **知识档案**：协作产生的知识自动沉淀为机器可读的档案，反哺所有人的 agent
- **蒸馏器**：讨论流 → 知识档案的自动提炼（AI 起草 + 人审合入）

## 2. 背景与问题（Why）

### 2.1 超级个体的下一站是超级团队

单人 + agent 团队（vibecoding 全链路）已成熟；但当任务规模超出单人时，团队成员各自的 agent 团队之间完全隔离：

1. **知识在 agent 而不在人**：任务如何执行、将要如何执行，最清楚的是 agent。人与人的交流退化为"把 agent 生成的文档/回答复制粘贴给对方"。
2. **指令散失**：mentor 在飞书/微信里的指令、团队规范散落在聊天流里，每次都要人和 agent 重新理解。
3. **冲突后置**：各成员的 agent 并行开发，接口变更、文件冲突在合并时才暴露。
4. **经验流失**：踩坑、技巧、决策散失在聊天与个人脑子里，新人爬坡慢。
5. **信息轰炸**：一个群装下开发/推进/学习/闲聊必然混乱；分多个群则入口爆炸。

### 2.2 设计原则（不可妥协的边界）

| 原则 | 内容 | 依据 |
|---|---|---|
| **不窥视** | agent 只上报工件与状态（claim/分支/diff 摘要/阻塞原因），不上报思考过程与私有上下文 | A2A "Preserve Opacity"；隐私与信任边界 |
| **窄接口** | agent 间不自由对话；通过任务、契约（spec）、PR 三种窄接口交互 | 通信拓扑研究：稀疏通信 80-99% 开销可省 |
| **人管工作** | 人类永远是人机混合团队的责任主体与仲裁者；agent 只起草，人审批 | Symphony 教训；Karpathy autonomy slider |
| **档流分离** | 持久知识（档）与即时讨论（流）是两种载体；IM 只是入口与出口 | CSCW 知识管理研究；Zulip/Discourse 实践 |
| **Git 为核** | 一切持久产物（任务、知识、代码）最终落在 Git 仓库，人读与 agent 读是同一份数据的两个视图 | docs-as-code；AGENTS.md 事实标准 |

## 3. 目标用户与画像

| 画像 | 描述 | 核心诉求 |
|---|---|---|
| **队长 / Mentor** | 拆解需求、验收、维护团队规范 | 指令不散失；成员进度一眼可见；新人能自助 |
| **成员（工程师）** | 带 agent 执行任务 | 少开会少刷群；不被别人冲突波及；agent 懂上下文 |
| **新人** | 刚加入团队 | 通过档案层 + agent 快速理解规范与历史决策 |

## 4. 场景与用户故事（P0 为 MVP 范围）

### 场景 A：任务从指令到验收（P0）

- A1 队长在 Web 看板创建任务，DoD（验收标准）必填，指定模块与负责人
- A2 成员的 daemon 自动或手动认领任务，服务端记会话状态
- A3 daemon 创建隔离 worktree，组装上下文（任务 + DoD + 关联 spec + 经验卡 + AGENTS.md）驱动本地 coding agent
- A4 agent 完成 → diff 统计回写 → 状态流转 waiting_review
- A5 队长在任务卡看到改动摘要与关联会话，验收 → done

### 场景 B：冲突提前暴露（P0）

- B1 两个成员的 agent 在途分支修改了同一文件 → 看板黄灯告警
- B2 某 PR 修改了被依赖的契约文件（spec 中声明的接口）→ 下游任务 owner 收到通知事件

### 场景 C：知识沉淀与消费（P0）

- C1 团队问答（Web 流/IM）中问题被解决 → 蒸馏器起草经验卡 → 人审合入档案
- C2 任何 agent 通过 MCP 检索档案：`search / read / propose / latest`
- C3 成员开发时，daemon 组装任务上下文自动注入相关 spec 与经验卡

### 场景 D：注意力管理（P1）

- D1 每日 digest：昨日任务迁移/告警/新增知识，一条消息
- D2 IM（飞书）作为入口：@共工 把一句话转成任务草案

### 场景 E：探讨与决策（P1）

- E1 探讨流出结论 → 蒸馏器起草 ADR → 人审合入
- E2 ADR 状态机：proposed → accepted → superseded

## 5. 功能需求清单

### F1 任务总线（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F1.1 | 任务 CRUD | 创建时 DoD 必填；支持标签/模块/负责人字段 |
| F1.2 | 状态机流转 | 非法迁移被拒绝并返回原因；每次迁移产生事件 |
| F1.3 | 依赖边 | 任务可声明上下游；环检测拒绝成环；下游变更发布通知事件 |
| F1.4 | 看板 | 按状态分列展示；卡片显示负责人/agent 会话/DoD/依赖 |

### F2 知识档案（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F2.1 | 五类知识对象 | spec/adr/card/reading/agent-doc，统一 front-matter（title/type/tags/owner/created/expires?） |
| F2.2 | 档案仓库 | knowledge/ 目录由 Git 管理；写入=提交；历史可查 |
| F2.3 | 检索 | 全文（含中文）+ 类型 + 标签过滤；返回引用路径 |
| F2.4 | 档案站 | 浏览/搜索/详情三个视图 |
| F2.5 | 过期治理 | 带 expires 的卡片到期被标记 stale（P1：蒸馏器起草归档 PR） |

### F3 MCP 接入层（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F3.1 | 四工具 | `search(query,filters)` / `read(path)` / `propose(draft)` / `latest(n)` |
| F3.2 | 可挂载 | zcode / Claude Code 可通过 stdio MCP 配置接入并完成一次真实检索 |

### F4 会话桥 daemon（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F4.1 | 注册与心跳 | daemon 以成员 token 注册，断线可恢复 |
| F4.2 | agent 适配 | 至少实现 Claude Code headless adapter；适配器接口可扩展 |
| F4.3 | 任务执行闭环 | 认领 → worktree → 注入上下文 → 执行 → 状态回写 → 提交分支 |
| F4.4 | 状态可见 | 看板实时显示每个会话的 claim/分支/状态/diff 摘要 |

### F5 冲突雷达（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F5.1 | 文件重叠告警 | 在途分支改动文件求交 > 阈值 → 告警事件 + 看板标记 |
| F5.2 | 契约变更通知 | PR 改动契约目录（specs/agents）→ 通知下游任务 owner |

### F6 蒸馏器（P1，MVP 期间实现第一条链路）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F6.1 | 事件订阅框架 | 消费 events outbox；规则可配置 |
| F6.2 | 问答→经验卡 | 标记 solved 的问答 → LLM 起草 card → propose 待人审 |
| F6.3 | 每日 digest | 聚合 24h 事件生成摘要（P1：推送 IM） |

### F7 IM 集成（P1）

- 飞书 bot：digest 推送、@共工 建任务草案。

## 6. 非功能需求

| 维度 | 要求 |
|---|---|
| 部署 | 50 人以下团队单机 docker-free 可跑（node + sqlite）；数据全部本地 |
| 性能 | 看板操作 P95 < 200ms（局域网）；FTS 检索 < 100ms（万级文档） |
| 安全 | 成员 token 认证；agent 无权越过 propose 流程直接写档案；propose 必须人审 |
| 可观测 | 结构化日志（pino）；关键链路有事件留痕 |
| 测试 | 每个子模块单元测试；核心逻辑（状态机/依赖图/front-matter/重叠分析）分支覆盖 |

## 7. 明确不做（Non-goals，MVP）

1. 不做 agent 间自由对话总线
2. 不做对本地 agent 屏幕级监控
3. 不做 A2A 联邦与跨组织互联（后续演进方向）
4. 不替代 Gitee/GitHub 的 PR 评审（MVP 用分支提交表达产出，PR 对接留给 GitProvider 扩展）
5. 不做多租户 SaaS
